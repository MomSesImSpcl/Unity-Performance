# Baseline anti-pattern checklist (review safety net — a floor, not a ceiling)

This checklist is a **fallback comparison table** for reviews: it guarantees you don't miss these deterministic problems, and you can cite its numbers directly in your output (e.g. #8, A3). It does **not** restrict you from producing findings and better solutions beyond the list — especially at the algorithmic layer, where your algorithmic repertoire far exceeds group A's table. Whenever you meet heavy computation, you must model it yourself (see [review-method.md](review-method.md)).

## Group A: algorithmic and redundant-computation anti-patterns (largest order-of-magnitude payoff — look here first)

| # | Anti-pattern | Problem | Fix |
|---|--------|------|------|
| A1 | Nested-loop pairing/lookup (iterating all of b for each a) | O(n²) — collapses as soon as the scale grows | Build a Dictionary/HashSet index on one side, dropping to O(n); pre-allocate and reuse the index container — don't introduce per-frame allocation for the sake of an algorithm |
| A2 | `List.Contains` / `Find` / `IndexOf` as a membership test on a hot path | An O(n) linear scan × the number of calls | Switch to HashSet/Dictionary above n ≈ 16; or maintain sorted order and binary-search |
| A3 | Recomputing an invariant result every frame (paths, stat totals, strings, layout) | Burning CPU for nothing | **Cache + dirty flag**: if the inputs haven't changed, use last time's result. Invalidate on events; don't poll and compare |
| A4 | Calling the same expensive function repeatedly within one frame (repeated GetComponent, repeated sorting, repeated distance computation) | In-frame redundancy | Cache within the frame (a local variable or a frame-number stamp); pass the result down the call chain instead of each site computing its own |
| A5 | A small change triggering full processing (one item changes, the whole inventory refreshes) | Solving an incremental problem in full | Incremental update: process only what changed (a dirty list, or events carrying the change set) |
| A6 | Sorting everything every frame, or a full sort just to get the max or top K | Sorting abuse | Top-1 is a linear scan; top-K uses a heap; nearly-sorted data is maintained by insertion |
| A7 | Rebuilding identical content repeatedly (same-argument strings, same result sets, same queries) | Result-level redundancy | A result dedup table (key → cache), reused on hit — with a capacity cap and an invalidation policy |
| A8 | Polling a low-frequency event at high frequency (checking "is the quest done" every frame) | Wasted polling | Switch to event/callback driven; where polling is unavoidable, lower the rate (a 0.2–0.5 s tick) |
| A9 | Forward per-item evaluation (calling the predicate once for every x against all y) | The predicate runs n×m times | **Reverse the iteration direction**: precompute the feasible set once into a HashSet or bitset, then the x side is an O(1) lookup; mark the feasible set dirty and recompute when the source data changes |
| A10 | Using List/HashSet for small-integer-domain sets (hand cards, slots, index markers, domain ≤64) | Allocation + hashing overhead | **Bitset it**: use `ulong` bit operations for intersection/union/difference/containment — all O(1), zero allocation (use `uint` for a domain ≤32; `Span<ulong>` in segments for larger) |
| A11 | Heavy search (backtracking, exhaustive) with no memoization and no pruning, re-run independently from multiple entry points | Exponentially repeated subproblems × the number of entry points | Memoize subproblem results and prune with upper/lower bounds; **hang the overall result cache off the single choke point where the data is modified** (funnel all inserts/updates/deletes through one entry) so multiple callers share one result |
| A12 | Looking only at a heavy function's single-call cost without accounting for the call-chain total (nested refresh chains: A calls B, B ends by calling C, and C runs A again inside) | Single-call cost × a hidden multiplier — one user action actually runs the heavy function 5–8 times | **Audit with "one user action" as the unit**: trace every entry point and nesting relationship of the heavy function and compute the total execution count for one action. The fix is to converge the cascading refresh onto a single entry point (dirty-flag driven) so one action executes it at most once |

**The hard rule where group A meets zero GC**: auxiliary structures introduced by an algorithmic optimization (index dictionaries, cache tables, heaps) must be pre-allocated, reused, and capped. You may not fix an "O(n²) problem" by creating a "new Dictionary every frame" problem — accept on both columns, time and GC Alloc.

## Group B: API usage and allocation anti-patterns

| # | Anti-pattern | Problem | Fix |
|---|--------|------|------|
| 1 | `GetComponent` / `Camera.main` (older versions) / `FindObjectOfType` inside Update; also looking up children by a **concatenated string name** on hot paths (`Transform.Find($"card_{i}")`, `GetAnchor($"...")`-style wrappers — interpolation allocation plus a name-by-name linear comparison) | Per-frame or per-event lookup cost | Cache the reference in Awake/Start; lookup APIs are only permitted during initialization; replace name lookups with **direct indexing into a serialized array by (enum, index)** — zero allocation, zero comparison |
| 2 | LINQ on hot paths, or `foreach` over an interface-typed collection | Hidden GC allocation | for loops over a List/array; LINQ only off hot paths |
| 3 | String concatenation / `$""` interpolation on hot paths | Per-frame string allocation | Cache invariant text; reuse a StringBuilder; format numbers with allocation-free APIs |
| 4 | Lambdas capturing outer variables / `new`ing a delegate every frame | Closure class allocation | Cache the delegate; use static lambdas; avoid subscribing/unsubscribing on hot paths |
| 5 | Value type boxing (object parameters, non-generic containers, concatenating an int into a string) | Boxing allocation | Generic APIs; supply a comparer for enum dictionary keys (on older runtimes) |
| 6 | `Instantiate` / `Destroy` of high-frequency objects (bullets, floating text, effects) | Allocation + GC + Awake cost | `UnityEngine.Pool.ObjectPool<T>` |
| 7 | Overloads of `Physics.Raycast` and friends that return arrays | Allocates an array each call | NonAlloc overloads / a pre-allocated buffer / batched RaycastCommand |
| 8 | Reading `renderer.material` | Silently instantiates a material copy (leak + broken batching) | `sharedMaterial` or `MaterialPropertyBlock` |
| 9 | Setting Animator/Shader parameters by string | Hashes the string every call | Cache ints with `Animator.StringToHash` / `Shader.PropertyToID` |
| 10 | `tag == "xxx"` / accessing `.tag` | String allocation + comparison | `CompareTag("xxx")` |
| 11 | `Vector3.Distance` used only for comparison | A wasted square root | Compare `sqrMagnitude` against a squared value |
| 12 | Hundreds or thousands of MonoBehaviours each with an empty or tiny Update | Per-object engine↔managed call overhead | Drive them from one manager; remove Update when it isn't needed |
| 13 | `new WaitForSeconds` inside a coroutine loop | Allocates every iteration | Cache the yield object; or switch to Awaitable/UniTask |
| 14 | `SetActive` toggling an entire UI tree every frame | Triggers rebuild + Awake | See ui-ugui-tmp.md (Canvas toggling / CanvasGroup) |
| 15 | `Resources.Load` synchronously loading a large asset / synchronously Instantiating a large batch at once | Main thread freeze / BigJank | Addressables async + preloading; for bulk instantiation use `InstantiateAsync` with per-frame integration (2022.3.20+) |
| 16 | Interpolation / `string.Join` / LINQ projection inside a log call's arguments | **Arguments are eagerly evaluated before the call** — with the log switch off, the allocation and computation happen anyway | Put `[Conditional("MACRO")]` on the log method (the whole call, argument evaluation included, is stripped at compile time); if that's impossible, wrap the call site in `#if`; never do collection projection inside log arguments |
| 17 | Reflection into private members as a fallback (`GetField(NonPublic)`) / reflection on hot paths | Slow + silently breaks when a field is renamed + AOT stripping risk | Have the data layer expose an explicit initialization/access interface (put the contract in the open); where dynamism is genuinely needed, cache a delegate at startup or use a source generator |
| 18 | `async void` + `Task.Delay` driving the timing logic of Unity objects | Three risks: the object may already be destroyed after the await (leaving the table, switching scenes) → NRE; `Task.Delay` ignores `Time.timeScale` and drifts out of sync with DOTween/animation durations; exceptions from async void have no receiver | Coroutine + a cached Wait object + a destruction guard; or UniTask + `GetCancellationTokenOnDestroy()`. At minimum, add a liveness check (`this != null` / IsValid) after every `await` before touching a Unity object |
| 19 | Using `Animator.Rebind()` as "reset the animation" (calling it on every playback or every phase); **the same family: flipping `animator.enabled = false→true` as a reset** (re-enabling likewise triggers rebinding and resets to default values, at comparable cost) | Rebind is one of Animator's most expensive calls: it rebuilds every binding cache and resets controlled properties to their defaults — which often forces the caller to write compensating "save → restore" logic (with incidental temporary array allocation), expensive on top of expensive | Add an explicit Idle/Reset empty state in the AnimatorController and return to it with `Play("Idle", 0, 0f)` (`Play(stateHash, layer, 0f)` already force-plays from the start, so most situations don't even need a reset); reserve Rebind for cases where the skeleton or binding structure genuinely changed |
| 20 | A polling wait with no timeout and no invalidation guard (`while(!cond) await Delay/yield`, where cond depends on normalizedTime or a flag set by a callback) | A "perpetual motion" leak: the object gets destroyed (an NRE inside the lambda swallowed by the Task), normalizedTime freezes once the Animator is disabled, OnComplete never arrives after a tween is Killed — the condition is never satisfied and the loop spins every N ms until the process exits | **Audit every wait point for "paths on which the condition is never satisfied"**; wrap it in a uniform waiting utility with three pieces: a null check, an enabled/activeInHierarchy check, and a timeout fallback. Where it can be event-driven (TaskCompletionSource, Animation Event, an OnComplete callback), don't poll |
| 21 | One-shot timeout / delay closures with no generation guard and no cancellation on the success path (request-response timeout fallbacks, DelayCall, room-entry and loading timeouts, and repeatedly triggerable wait coroutines) | Three symptoms: (1) after success, the timeout closure still lives out its full duration, holding captured references; (2) a new round of the same operation and the old closure contaminate each other — the old timeout fires with old arguments and wrongly fails the new operation; (3) repeated triggering stacks multiple wait coroutines/tasks that all release the instant the condition is met (duplicate protocol sends, duplicate callbacks). There is also "mutual exclusion by msgId silently dropping subsequent requests," which leaves taps with no feedback | **Generation guard**: an incrementing seq captured by the closure; on firing, ignore it if it doesn't match the current one. **Explicitly cancel** the timeout closure on the success path (Cancel/Dispose). **One handle per class of wait**: stop the previous one before starting a new one (cache the Coroutine/CTS in a field). Mutual-exclusion drops must give UI feedback or become overwrite semantics |
| 22 | Synchronous system calls on critical frames (startup / login / scene change / entering a room): explicit `PlayerPrefs.Save()`, reading the system clipboard (`GUIUtility.systemCopyBuffer`), repeatedly calling JNI platform APIs like `SystemInfo.deviceUniqueIdentifier`, synchronous file IO | Those frames are already the most crowded (loading + UI construction + network responses); piling a synchronous disk flush, a JNI call, or a clipboard read on top (which can block for hundreds of ms on iOS and raise a privacy prompt) directly lengthens the moment the user feels most | Cache process-invariant values (device ID and the like) once statically; delete explicit Save/flush calls (leave it to the engine lifecycle) or move them to an idle frame; defer reading system resources like the clipboard until they're actually consumed. **Audit method: list the critical frame's call chain and check it for synchronous system calls one by one** |
| 23 | Bare access to a singleton `Instance` getter whose implicit instantiation has side effects (MonoSingleton classes: with no instance, it does new GameObject + AddComponent + a full set of event/message registrations) | A "just reading some state" context accidentally creates an entire system — usually on the busiest frame. The subtler form: **someone in the file already established a `HasInstance()` guard convention (even with a comment), but the other call sites don't follow it** | Always guard read contexts with `HasInstance()` before accessing (return the semantically equivalent value directly when there's no instance). **Once you find a guard pattern, you must grep every comparable call site and check consistency — "a guard exists" ≠ "the guard is followed"** |
| 24 | Storing an entire network message or large data object in a member field when only one or two scalars from it are ever read afterwards (keeping the login response or a full config push in a field just to check a bool) | The large object lingers for the host's lifetime and can't be collected (and may also block the message object pool from recycling); the Mono heap only rises, and this kind of retention directly raises the lifetime water level | Extract the scalars you need into their own fields immediately after consumption and null the large object reference. Audit method: for every message type stored in a field, ask "what am I actually reading out of this whole object?" |
